01 · Product

What it does

PRFlow watches the repositories a user has connected, pulls every pull request from GitHub on a schedule, and turns the resulting pile into a prioritized, explainable work list. The system solves a very specific problem: engineering teams that have more open PRs than reviewers can comfortably handle, and no way to tell which one is going to bite them first.

Scoring

Priority Engine

Every PR is scored across 8 signals (age, reviewers, conflicts, CI, blockers, labels) and bucketed into Low / Medium / High / Critical.

Graph

Dependency Graph

Auto-extracts "depends on #N" / "blocked by #N" / "requires #N" from PR bodies and renders the chain visually with ReactFlow.

Load

Reviewer Workload

Counts currently-requested reviews per reviewer, computes load vs. capacity, and flags overload.

Alerts

Proactive Alerts

Critical PRs, merge conflicts, blocked dependencies, and reviewer overload become dismissible alerts. Stale alerts auto-clear when the condition resolves.

Analytics

Engineering Trends

Weekly aggregates of review time, merge time, PR volume, and bottleneck frequency for 2W / 4W / 6W / 3M windows.

Auth

GitHub OAuth + JWT

Email/password OR GitHub OAuth. The OAuth token is persisted per user so private repos sync correctly without exposing it to the browser.

02 · Architecture

Architecture

A clean two-process setup: Vite + React 18 on the front, FastAPI behind it talking to PostgreSQL. A background scheduler (APScheduler) ticks every SYNC_INTERVAL_MINUTES and pulls fresh data from the GitHub REST API into the database. The UI never hits GitHub directly — it always reads from the DB through REST endpoints.

Browser

React 18 + Vite, React Router 7, ReactFlow, Framer Motion, Three.js (3D backgrounds).

REST API

FastAPI routers per resource. JWT bearer auth, CORS open in dev, error-handled.

Services

SyncService · PriorityService · ReviewerService · AnalyticsService · AlertService · GitHubService.

Scheduler

APScheduler background job. Per-repo isolation, rate-limit aware, non-fatal failures.

Notable design choice: the DB is the source of truth for the UI. GitHub is treated as an upstream data source whose values are pulled on a cadence and stored locally. This means the dashboard, the dependency graph, and the analytics charts are all read-only DB queries — no per-request GitHub hammering.

04 · Priority engine

Priority engine

The priority engine is the heart of the product. It is implemented in app/analyzers/priority_engine.py as a pure function: calculate_priority(pr_data) → {score, level, breakdown}. Eight signals are summed, then bucketed.

The eight scoring factors

FactorSourceWhy it matters
AgePR.created_atStale PRs are technical debt in disguise.
Pending reviewsPRReviewer rowsMore pending reviewers = more coordination cost = more likely to stall.
Merge conflictpr.mergeable == falseAuthor must rebase; PR is effectively dead until they do.
Failing CIper-SHA check APIReviewers ignore red PRs; merge risk goes up.
Is blockingreversed Dependency rowsIf other PRs depend on this one, every day it doesn't merge blocks more work.
Urgent labellabel == "urgent"Human-asserted priority signal.
Bug labellabel == "bug"Production-shape risk.
Security labellabel == "security"Highest class of risk; weighted higher than bug.

The final score is bucketed using LOW_THRESHOLD / MEDIUM_THRESHOLD / HIGH_THRESHOLD constants into Low / Medium / High / Critical. The breakdown is returned alongside the score so the UI can show why a PR is critical — not just that it is.

Interview view — how the engine works end-to-end

  1. SyncService fetches PRs from GitHub and enriches them with three signals GitHub's PR-list endpoint doesn't return inline: pending_reviews, failing_checks, is_blocking.
  2. PriorityService calls calculate_priority on each enriched PR.
  3. Score, level, and per-factor breakdown are written to the pull_requests row alongside the raw PR data.
  4. AlertService then looks at every Critical PR and creates a "critical_pr" alert — but only if one doesn't already exist for that PR.
05 · Sync pipeline

Sync pipeline

The SyncService is the most important service in the codebase. It runs once on startup (in a background thread so the API comes up fast) and then on a timer. Each iteration:

1. List repos

Pulls every repo the user has explicitly added. Per-user scoping (no fan-out from a global token).

2. Fetch PRs

Per-repo, with the user's OAuth token if available — falls back to the server-wide token. Paginates up to 5 × 100 = 500 PRs.

3. Enrich

Adds pending_reviews, failing_checks, is_blocking so the priority engine has real signals.

4. Score

Runs the priority engine on every PR. Stores score, level, and breakdown.

5. Upsert

Creates or updates each PR row. Marks status="merged" if GitHub says merged_at is set, else "open"/"closed".

6. Dependencies

Scans PR bodies for "depends on #N / blocked by #N / requires #N" regex and creates Dependency rows.

7. Reviewers

Creates Reviewer + PRReviewer link rows from requested_reviewers. Marks stale "requested" links as "reviewed".

8. Reviews

For open PRs only, pulls the actual review history to compute first_review_at and power the timeline.

Failure isolation: one repo failing (bad token, 404, rate-limit on that endpoint) does not stop the others. A global rate-limit on the auth token, however, halts the whole batch so we don't burn 30 minutes logging the same 403 for every subsequent repo.

06 · Alerts & reviewer load

Alerts & reviewer workload

Four alert types, idempotent regeneration

  • critical_pr — priority_level == "Critical" and not merged/closed.
  • merge_conflict — merge_conflict == True and not merged/closed.
  • blocked_dependency — has a Dependency pointing into it whose source is still open.
  • reviewer_overload — load_percent > 100% (active PRs > reviewer.capacity).

Each generator first looks for an open alert of the same type for the same PR/reviewer; if found, it skips. At the end it deletes any alert whose underlying condition no longer holds. Net effect: alerts self-clear the moment the condition goes away — no manual "dismiss" required, and no duplicates pile up across syncs.

Reviewer workload formula

For each reviewer that has any currently-requested PR in this user's repos: 

# app/analyzers/reviewer_analyzer.py
active_count   = len(assigned_prs)     # real current request list
capacity       = reviewer.capacity or 1
load_percent   = round((active_count / capacity) * 100)

status = "overloaded"  if load_percent >  100
       = "busy"        if load_percent >= 70
       = "available"   otherwise

Reviewers are sorted by load descending, so the most-buried are always at the top of the table.

07 · Dependency graph

Dependency graph

The dependency graph is the most distinctive UI in the app. It is built server-side by DependencyGraphService and returned in the exact shape reactflow expects.

How edges get discovered

During sync, every PR body is scanned with a regex: 

regex: (?:depends on|blocked by|requires)\s*#(\d+)

If PR #42's body contains "Depends on #15", we create a Dependency where source_pr_id = 15 (must merge first) and target_pr_id = 42 (is blocked). The graph is therefore drawn left-to-right: prerequisites on the left, blocked PRs to their right.

Layout: levels via longest path

# app/services/dependency_graph_service.py
level(pr) = 0                          # no incoming deps
level(pr) = 1 + max(level(p) for p in incoming(pr))   # otherwise

Cycles are guarded against with a recursion set. Nodes are color-coded by priority level (Critical amber, High blue, Medium violet, Low green). Edges animate while the upstream PR is unmerged.

09 · Auth & OAuth

Auth & OAuth

Two ways in:

  • Email / password — bcrypt-hashed via passlib, JWT issued via python-jose, stored in localStorage on the client and sent as a Bearer token on every request.
  • GitHub OAuth — full authorize → callback flow, with the state parameter signed into a cookie via itsdangerous-backed SessionMiddleware. The returned access token is stored on the User row and used as a per-user fallback when the server-wide token can't see the repo.

A single 401 from any endpoint is enough to drop the user cleanly to the unauthorized page — handled by a global handler installed in AppContext and triggered from the central apiRequest wrapper.

11 · Interview Q&A

Likely interview questions

Twenty-two questions ordered roughly easy → harder, with concise answers you'd actually say in an interview.

What does PRFlow actually do? Who is it for?
A self-hosted engineering intelligence layer on top of GitHub. It pulls PRs, scores them with a priority engine, shows reviewer workload and dependency chains, and surfaces alerts. Target user: a tech lead or staff engineer trying to triage a backlog of open PRs across multiple repos.
Walk me through the architecture.
React 18 + Vite frontend talking to a FastAPI backend. Backend uses SQLAlchemy against PostgreSQL. An APScheduler background job runs SyncService.full_sync on a fixed interval, pulls data from GitHub into the DB, and the UI reads only from the DB. CORS is open in dev, JWT bearer auth protects the app routes, and per-user GitHub OAuth tokens are stored for private repo access.
How is the priority score calculated?
Sum of weighted signals: age of PR, count of pending reviewers, merge conflict, failing CI, whether the PR is blocking other PRs, and the presence of "urgent", "bug", or "security" labels. The total is bucketed into Low / Medium / High / Critical via threshold constants in app/constants/priority_rules.py. Each factor is returned in a breakdown list so the UI can show "why".
Why is the priority engine a pure function?
So it's testable without the DB. calculate_priority(pr_dict) → {score, level, breakdown} only depends on its input. That makes it trivial to unit test edge cases (10-day-old PR, three pending reviewers, security label, etc.) by feeding in dicts.
How are dependencies between PRs discovered?
A regex over each PR body for "depends on #N", "blocked by #N", or "requires #N". If a body contains "Depends on #15", a Dependency row is created with source_pr_id = 15 (must merge first) and target_pr_id = current (is blocked). The graph service then computes longest-path levels for left-to-right layout and guards against cycles via a recursion set.
What happens if the GitHub API rate-limits you mid-sync?
The service catches GitHubRateLimitError per repository. A rate limit on a single endpoint (e.g. fetching CI checks) stops processing only for that repo. A rate limit that affects the whole token (e.g. listing PRs) halts the whole batch — otherwise every subsequent repo would log the same 403 and burn the rest of the window.
Why store data in a DB at all? Why not just call GitHub live?
Three reasons: (1) rate limits — the GitHub REST API caps at 5,000 req/h for an authenticated user, and we can hit that with a handful of repos. (2) Latency — analytics pages aggregate over weeks of data; computing that on every page load is wasteful. (3) The dependency graph and reviewer workload need to combine data from many PRs and reviewers in a single query. Caching the upstream and querying locally is faster and cheaper.
How is the DB kept fresh?
APScheduler runs full_sync on a fixed interval (configurable via SYNC_INTERVAL_MINUTES). One full sweep on startup in a background thread so the API can serve traffic immediately. Each PR is upserted — existing rows are updated, new ones are created, and the merge/closed state is normalized from GitHub's state + merged_at.
Explain the alert system.
Four generators: critical PRs, merge conflicts, blocked dependencies, reviewer overload. Each generator is idempotent — it won't duplicate an alert for a condition that's already flagged, and at the end of each run it deletes any alert whose condition no longer holds. Net effect: alerts self-clear as the underlying problem resolves, no manual "dismiss" needed.
How is reviewer workload computed?
For each reviewer with at least one currently-requested PR in this user's repos, count the active PRs and divide by the reviewer's configured capacity. load_percent > 100% is overloaded, ≥ 70% is busy, otherwise available. The result is sorted by load descending so the most buried appear first.
How does auth work?
Two paths. Email/password: bcrypt-hashed, JWT issued via python-jose, stored in localStorage on the client, sent as a Bearer token. GitHub OAuth: full authorize → callback, the state param signed into a cookie via itsdangerous, the returned access token saved on the User row for per-user syncing of private repos. A single 401 from any API call drops the user to the unauthorized page via a global handler.
What is the "depends on" / "blocked by" / "requires" regex?
(?:depends on|blocked by|requires)\s*#(\d+), case-insensitive. It matches phrases like "depends on #15", "Blocked by #27", "requires #9", and captures the PR number. Anything else (e.g. "depends on branch foo") is ignored.
Why do you enrich the PRs before scoring?
GitHub's PR-list endpoint returns requested_reviewers inline but doesn't return CI status or the blocking status. Without enrichment, three of the eight priority factors would always be zero and the engine would systematically underestimate risk. So before scoring we (a) count requested_reviewers, (b) call the checks API per open PR's head SHA, and (c) scan the body text for "depends on #N" to mark the referenced PR as is_blocking.
How are stale "requested" reviewer links handled?
After each sync, we compare the GitHub-returned requested_reviewers set for that PR to what's stored. Any stored link that isn't in the current set is presumed to have already reviewed and is updated from "requested" to "reviewed". This keeps Reviewer.pending_reviews accurate without an explicit "I just reviewed" event.
Why ReactFlow for the dependency graph?
It's the standard React library for node-edge visualizations with built-in pan/zoom, mini-map, and custom node types. The backend already returns data in reactflow's { nodes, edges } shape, so the frontend just maps it. Custom node components render the PR number, title, priority chip, and status with priority-driven colors.
How would you scale this to 10,000 PRs per repo?
Several answers: (1) the sync already caps at 5 pages × 100 = 500 PRs per repo, so the first change is raising that cap and adding incremental sync by updated_at. (2) Move heavy aggregations to materialized views or a dedicated analytics schema. (3) Pre-compute priority and reviewer workload in the background rather than on read. (4) Cache dependency graph layouts. (5) The priority engine itself is O(n) per PR so it scales linearly — no algorithmic change needed.
What would you do differently if you started over?
A few honest answers: introduce Celery or a real queue (RQ / Arq) instead of APScheduler for background work, so jobs survive restarts and are observable. Add an OpenTelemetry exporter for the GitHub HTTP client so we can see per-call latency. Make the priority engine configurable per-org (different teams weight things differently). And add a small admin tool for replaying one repo's sync with verbose logs — invaluable when triaging "why is this PR not showing up?"
What security considerations did you handle?
Passwords are bcrypt-hashed, never stored plaintext. JWTs are signed and stored client-side; a single 401 globally logs the user out. GitHub OAuth state is signed via itsdangerous to prevent CSRF. Per-user access tokens are stored server-side and never returned in API responses. CORS is locked down in production (it's only wide-open in dev). SQL is parameterized via SQLAlchemy ORM so there's no string-injection risk. password_hash and github_access_token are explicit fields on the User model and should be excluded from any public schema.
Why FastAPI instead of Flask or Django?
FastAPI gives us Pydantic-validated request/response models for free, async handlers when we need them, automatic OpenAPI docs (handy for the frontend team), and clean dependency injection for the DB session. Django would have been heavier than needed for what's basically a thin REST + scheduler. Flask is fine but I'd be reimplementing half of what FastAPI ships with.
How is the data model related?
User has many Repositories. Each Repository has many PullRequests. PR ↔ Reviewer is many-to-many through PRReviewer (with a status). PRReview stores the actual submitted review (one row per submitted review, with timestamp). Dependency is a self-relation on PR via source_pr_id / target_pr_id. Alert belongs to User and optionally to a PR or Reviewer.
What does the dependency graph layout algorithm do?
It assigns each PR a "level" = length of the longest chain of dependencies leading into it. A PR with no prerequisites is level 0; a PR whose prerequisites are themselves level 0 is level 1; and so on. Nodes are placed at x = level * 260 and stacked down the y axis, producing a left-to-right DAG. A recursion set guards against cycles, which would otherwise loop forever.
How do you test this?
The analyzers are pure functions — directly unit-testable. Services are tested by injecting a SQLAlchemy session against a SQLite or test PostgreSQL. The GitHub client is mocked at the requests boundary in tests/. The priority engine has a dedicated SyncService_test.py-style fixture pattern; full repo-level integration is exercised via the FastAPI app with the dependency overrides swapped out.
What is the hardest bug you've had to chase in this project?
A good answer would be the priority engine systematically under-reporting risk: scores were "always low" because the engine was being fed PRs that hadn't been enriched with pending_reviews, failing_checks, and is_blocking — three factors the GitHub PR-list endpoint doesn't return. Fix was to enrich before scoring, not after. Worth mentioning because it's a great example of "the bug is in the orchestration order, not the logic".
12 · Additions

Things worth adding that aren't here yet

From my own read of the codebase, a few pieces are missing or worth strengthening before shipping this to more than one team:

  • Real-time updates. Everything is poll-based via APScheduler. Adding a webhook receiver for GitHub's pull_request and pull_request_review events would let scores refresh instantly when a label is added, a review is submitted, or a PR is merged.
  • Queue-backed sync. APScheduler runs the job in-process; a restart drops in-flight work. A proper queue (Celery, RQ, or even just an outbox table polled by a worker) would be more durable.
  • Multi-tenant RBAC. Repositories are scoped to a user, but a team shared workspace with role-based read/write would unlock org-level adoption.
  • Slack / email notifications for high-priority alerts. Right now alerts only show in the app. Pushing them to a channel the team already watches is a 10× unlock.
  • Configurable priority weights. The constants in priority_rules.py are global. Surfacing them in Settings per-user or per-org would let teams tune "security label is +50 here, +200 there".
  • Per-PR activity timeline. The reviews are stored, and first_review_at is computed, but a true timeline (commits, comments, label changes, reviews) would be a great add for the PR detail page.
  • Test coverage report. backend/app/tests/ exists; running pytest with --cov and wiring it into CI would close a soft spot.
  • Observability. Adding prometheus_client middleware and shipping request latency + GitHub-call counters would make production debugging much easier.
  • Configurable dependency keywords per repo. Some teams say "needs", "after", "part of #N". The current regex would need light tuning to match their conventions.
  • CI status for non-GitHub-Actions check runs. The checks API only covers GitHub-Actions-style status checks; external CI (CircleCI, Buildkite) needs the check-runs endpoint for full coverage.
